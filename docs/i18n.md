# Mona UI Internationalization (i18n) & RTL Guide

Mona UI provides a comprehensive, signal-based internationalization (i18n) and localization architecture designed for modern Angular applications.

---

## 1. Core Principles

- **Zero-Config English:** Applications work out of the box with built-in English fallbacks. No setup or provider registration is required if you only need English.
- **Reactive Runtime Locale Switching:** Switching locales via `MonaI18nService.use()` instantly updates all rendered components across the application without requiring page reloads or component re-instantiation.
- **Strictly-Typed Namespaces:** Message interfaces are strongly typed per component namespace (`MonaLocaleMessages`), preventing typos and enabling full autocomplete.
- **Hierarchical Precedence:** A predictable cascade governs all user-facing strings (Component Input > Runtime Override > Active Locale > Component English Fallback).
- **Separation of Locale and Layout Direction:** Translation locale metadata (`MonaLocale.direction`) is strictly decoupled from physical DOM layout direction. Mona components follow the actual inherited DOM/CDK direction (`dir="ltr"` or `dir="rtl"`).

---

## 2. Official Locales (`@nanahoshi/mona-ui/locales`)

Mona UI provides official, framework-maintained locale packages exported via the secondary entry point:

```typescript
@nanahoshi/mona-ui/locales
```

### Supported Official Locales

| Locale Tag | Language | Constant | Direction | Completeness |
|---|---|---|---|---|
| `es-ES` | Spanish (Spain) | `MONA_ES_ES_LOCALE` | LTR | 100% (all 40 namespaces) |
| `de-DE` | German (Germany) | `MONA_DE_DE_LOCALE` | LTR | 100% (all 40 namespaces) |
| `fr-FR` | French (France) | `MONA_FR_FR_LOCALE` | LTR | 100% (all 40 namespaces) |
| `ja-JP` | Japanese (Japan) | `MONA_JA_JP_LOCALE` | LTR | 100% (all 40 namespaces) |

- **Regional Scope Note:** `fr-FR` is the official French (France) locale. Regional French variants such as `fr-CA` are separate locales and are not aliases of `fr-FR`. Likewise, `ja-JP` is the official Japanese (Japan) locale; there is no generic `ja` alias.
- **Zero Configuration for English:** English (`en-US`) is built directly into all component families as default fallbacks. No application requires importing `@nanahoshi/mona-ui/locales` unless opting into an official non-English locale.
- **Official vs. Application-Defined Locales:**
  - **Official Mona Locales:** Complete catalogs maintained by Mona UI. Official locale catalogs are compile-time structurally complete via `satisfies MonaLocaleMessages`: every required namespace, message key, and function signature must be implemented. Linguistic correctness is enforced separately through locale review and locale-specific tests/audits. A future addition of a required key causes compilation to fail until the translation is added.
  - **Application-Defined Locales:** Defined using `MonaLocale` with partial message subsets (`DeepPartial<MonaLocaleMessages>`). Any omitted keys automatically fall back to the component default English catalog.
- **Direction Separation:** Official locale direction metadata (e.g., `MONA_ES_ES_LOCALE.direction`, `MONA_DE_DE_LOCALE.direction`, `MONA_FR_FR_LOCALE.direction`, `MONA_JA_JP_LOCALE.direction`) describes the language's conventional reading direction (`ltr`). Selecting an official locale does not mutate DOM `dir`, CDK directionality, or semantic direction roots. Layout and interaction direction continue to follow semantic document/CDK directionality.

### Using an Official Locale at Startup

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideMonaI18n } from '@nanahoshi/mona-ui/i18n';
import { MONA_DE_DE_LOCALE } from '@nanahoshi/mona-ui/locales';

export const appConfig: ApplicationConfig = {
    providers: [
        provideMonaI18n({
            locale: MONA_DE_DE_LOCALE
        })
    ]
};
```

### Runtime Switching to an Official Locale

```typescript
import { Component, inject } from '@angular/core';
import { MonaI18nService, MONA_DEFAULT_LOCALE } from '@nanahoshi/mona-ui/i18n';
import { MONA_DE_DE_LOCALE, MONA_ES_ES_LOCALE, MONA_FR_FR_LOCALE, MONA_JA_JP_LOCALE } from '@nanahoshi/mona-ui/locales';

@Component({
    selector: 'app-language-toggle',
    template: `
        <button (click)="switchToGerman()">Deutsch (Deutschland)</button>
        <button (click)="switchToSpanish()">Español (España)</button>
        <button (click)="switchToFrench()">Français (France)</button>
        <button (click)="switchToJapanese()">日本語 (日本)</button>
        <button (click)="switchToEnglish()">English</button>
    `
})
export class LanguageToggleComponent {
    private readonly i18n = inject(MonaI18nService);

    public switchToGerman(): void {
        this.i18n.use(MONA_DE_DE_LOCALE);
    }

    public switchToSpanish(): void {
        this.i18n.use(MONA_ES_ES_LOCALE);
    }

    public switchToFrench(): void {
        this.i18n.use(MONA_FR_FR_LOCALE);
    }

    public switchToJapanese(): void {
        this.i18n.use(MONA_JA_JP_LOCALE);
    }

    public switchToEnglish(): void {
        this.i18n.use(MONA_DEFAULT_LOCALE);
    }
}
```

## 3. Configuration & Providers

To configure Mona UI with an initial locale or custom message overrides, use `provideMonaI18n()` in your application config:

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideMonaI18n, type MonaLocale } from '@nanahoshi/mona-ui/i18n';

const customTurkishLocale: MonaLocale = {
    id: 'tr-TR',
    direction: 'ltr',
    messages: {
        pager: {
            firstPageLabel: 'İlk sayfa',
            nextPageLabel: 'Sonraki sayfa',
            previousPageLabel: 'Önceki sayfa',
            lastPageLabel: 'Son sayfa',
            pageLabel: (page: number) => `Sayfa ${page}`
        }
    }
};

export const appConfig: ApplicationConfig = {
    providers: [
        provideMonaI18n({
            locale: customTurkishLocale
        })
    ]
};
```

## 4. The `MonaLocale` Contract

A Mona locale is defined by:

```typescript
export interface MonaLocale {
    /** BCP 47 locale tag, e.g. "en-US", "de-DE", "tr-TR", "ar-SA" */
    readonly id: string;

    /** Conventional writing direction associated with the locale ("ltr" or "rtl") */
    readonly direction: 'ltr' | 'rtl';

    /** Deep partial messages structured by component namespace */
    readonly messages: DeepPartial<MonaLocaleMessages>;
}
```

### Typed Message Namespaces

Each component family owns a distinct message namespace under `MonaLocaleMessages`, such as:
- `autoComplete`
- `breadcrumb`
- `calendar`
- `chart`
- `editor`
- `filter`
- `grid`
- `numericTextBox`
- `pager`
- `scrollView`
- `tabs`
- ...and all other Mona UI components.

Typo namespaces fail at compile-time:

```typescript
const invalidLocale: MonaLocale = {
    id: 'en-US',
    direction: 'ltr',
    messages: {
        // @ts-expect-error Typos fail compile-time validation
        pagre: {}
    }
};
```

## 5. Runtime Locale Switching

Inject `MonaI18nService` anywhere in your application to switch the active locale reactively:

```typescript
import { Component, inject } from '@angular/core';
import { MonaI18nService, type MonaLocale } from '@nanahoshi/mona-ui/i18n';

@Component({
    selector: 'app-language-switcher',
    template: `
        <button (click)="switchToTurkish()">Türkçe</button>
        <button (click)="switchToGerman()">Deutsch</button>
        <button (click)="switchToEnglish()">English</button>
    `
})
export class LanguageSwitcherComponent {
    private readonly i18n = inject(MonaI18nService);

    public switchToTurkish(): void {
        this.i18n.use({
            id: 'tr-TR',
            direction: 'ltr',
            messages: { /* Turkish translations */ }
        });
    }

    public switchToGerman(): void {
        this.i18n.use({
            id: 'de-DE',
            direction: 'ltr',
            messages: { /* German translations */ }
        });
    }

    public switchToEnglish(): void {
        this.i18n.use({
            id: 'en-US',
            direction: 'ltr',
            messages: {}
        });
    }
}
```

## 6. Runtime Message Overrides

If you want to customize specific strings across the entire application without replacing the active locale, use the override APIs:

- **`setMessages(overrides)`**: Replaces all active application-level overrides.
- **`patchMessages(partialOverrides)`**: Merges new overrides into existing ones without discarding others.
- **`clearMessages()`**: Clears all application overrides, restoring the active locale's values.

```typescript
// Override pager labels globally
i18n.patchMessages({
    pager: {
        nextPageLabel: 'Next >>'
    }
});

// Remove all global overrides
i18n.clearMessages();
```

---

## 7. Message Override Precedence

When a component resolves a user-facing label or announcement, the resolution order is strictly:

1. **Explicit Component Input:** A direct property binding on the component (e.g. `[ariaLabel]="'Custom'"` or custom templates).
2. **Application Runtime Overrides:** Messages set via `setMessages()` or `patchMessages()`.
3. **Active Locale Messages:** Messages provided in the current `MonaLocale` via `use()`.
4. **Component English Fallback:** Built-in default English catalog.

## 8. Locale vs. Layout Direction (RTL Architecture)

> [!IMPORTANT]
> `MonaLocale.direction` describes the conventional writing direction of the translation language. Mona UI does **NOT** automatically mutate `<html dir="...">` or subtree `dir` attributes.
>
> All direction-sensitive component behaviors (keyboard arrow navigation, animations, carousels, progress bar clipping, scroll offsets) follow the **semantic document directionality** resolved hierarchically:
> 1. **Connected Browser Semantic Direction (`:dir(rtl)` / `:dir(ltr)`):** In connected browser environments supporting `:dir()`, the browser's semantic document directionality is resolved (including native first-strong character resolution for `dir="auto"`). This guarantees exact alignment with Tailwind's `rtl:` and `ltr:` conditional variant styles.
> 2. **Explicit Ancestor `[dir]` Hierarchy:** In unattached DOM trees or environments without `:dir()` support, the nearest valid ancestor `dir` attribute (`ltr`, `rtl`, or `auto`) is resolved.
> 3. **Angular CDK `Directionality`:** Application-level direction fallback.
> 4. Default fallback: `'ltr'`.
>
> Mona's direction-sensitive behavior follows semantic document directionality (`dir`, inherited HTML directionality, and CDK direction state). Do not use the CSS `direction` property alone to switch Mona components between LTR and RTL behavior.

This ensures full support for:
- An Arabic locale rendered inside an LTR technical layout (`dir="ltr"`).
- An English locale rendered inside an RTL layout (`dir="rtl"`).
- Mixed LTR and RTL subtrees co-existing on the same page under a single `MonaI18nService` instance.

### RTL Guarantees & Logical Interactions

Mona UI provides complete **RTL and logical-layout support**:

#### Preferred Default: CSS Logical Properties & Utilities
For ordinary content, padding, margins, and layout flow that naturally follow the CSS writing direction:
- **CSS Logical Properties:** General UI layouts use CSS Logical Properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start/end`).
- **Logical Tailwind Utilities:** Tailwind utility classes use logical equivalents (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`).

#### Intentional Semantic-Physical Layout Exceptions
For interaction-critical geometry whose behavioral axis follows Mona semantic direction (`dir` attribute / CDK directionality) and must remain stable even when CSS `direction` is independently overridden, Mona explicitly maps semantic `start/end` to physical `left/right` coordinates:
- **Slider & RangeSlider:** Handles, selection fill bands, ticks, and label coordinates map semantic start/end to physical left/right coordinates to ensure the visual track and keyboard navigation direction match semantic direction even when CSS writing direction is decoupled.
- **Sidebar Docked Layout & Drawers:** Start and end sidebars, interior separator borders, collapse rail edges, and offcanvas drawer translations map to explicit physical coordinates according to semantic direction.
  > [!NOTE]
  > Computed CSS direction may be read as a rendering-compensation input; it does not become Mona's semantic behavior source.
- **ScrollView:** Carousel Previous/Next navigation controls pin to explicit physical edges according to semantic direction, and directional chevron icons mirror orientation (`rtl:rotate-180`).

These exceptions are **deliberate**, **strictly audited** via the i18n scanner, **narrowly allowlisted**, and **end-to-end browser tested** across all four LTR/RTL and split-direction matrices.

#### Direction-Aware Behaviors & Tracking
- **Icon Mirroring:** Directional chevrons and navigation arrows automatically mirror in RTL (`rtl:rotate-180`).
- **Direction-Aware Keyboard Navigation:**
  - **Pager:** Arrow keys navigate logically (`ArrowLeft` navigates to the next page in RTL, previous page in LTR; `ArrowRight` navigates to the previous page in RTL, next page in LTR).
  - **Calendar:** Arrow keys step forward/backward logically across day, month, year, and decade cells (`ArrowLeft` steps forward by 1 unit in RTL, backward in LTR; `ArrowRight` steps backward in RTL, forward in LTR).
  - **Slider & RangeSlider:** Arrow keys increase/decrease values in accordance with semantic direction (in RTL, `ArrowLeft` increases value and moves the handle leftward; `ArrowRight` decreases value and moves the handle rightward).
- **Logical Drag & Resize:**
  - **Grid Column Resizing:** Resize delta is inverted in RTL layouts so dragging in the visual inline-end direction increases column width and dragging inline-start decreases it intuitively.
- **Direction-Aware Visual Encodings:**
  - **Chart Color Scales:** Horizontal color scales and gradients mirror orientation in RTL to maintain logical scale progression.
- **Subtree Direction Tracking & Reactive Boundaries:**
  - Direction-sensitive components observe changes via MutationObserver for semantic `dir` attribute changes (`ltr`, `rtl`, `auto`), content mutations inside `dir="auto"` subtrees (re-evaluating first-strong directional characters), and Angular CDK `Directionality` changes.
  - **Reactive Boundary:** Runtime updates must be performed via semantic `dir` attributes or Angular CDK directionality. CSS `direction` alone does not match Tailwind's `:dir()` variants and is outside the component behavioral direction boundary. Moving components across pre-existing direction roots (reparenting) should be accompanied by updating semantic `dir` attributes.

## 9. Formatting & Angular `LOCALE_ID` Independence

Mona UI components format numbers, currencies, dates, and times using `MonaI18nService.localeId()` directly:
- **`NumericTextBoxComponent` & Locale Formatters:**
  - **Dynamic Grouping Pattern Derivation:** Automatically discovers the locale's primary and secondary grouping sizes, canonical group separator, and minimum grouping threshold from `Intl.NumberFormat`:
    - **Western Grouping:** 3-3-3 digit groupings (e.g. `1,234,567.89` in `en-US`, `1.234.567,89` in `de-DE`).
    - **Indian Grouping:** 3-2-2 digit groupings (e.g. `1,23,45,678.9` in `hi-IN`, `en-IN`, `bn-BD`, `mr-IN`).
    - **Arabic & Eastern Numbering:** Canonical Arabic thousand separator (`\u066C`) and Arabic-Indic / Eastern Arabic-Indic digits (e.g. `ar-SA`, `fa-IR`).
    - **Space-Delimited Separators:** Strictly accepts canonical space variants (regular space `\u0020`, non-breaking space `\u00A0`, narrow no-break space `\u202F`) while rejecting other whitespace (tabs, newlines, form feeds) in strict mode (e.g. `fr-FR`).
  - **Strict ("locale") vs. Interactive ("edit") Parsing Modes:**
    - **Strict Mode (`mode: "locale"`):** Enforces canonical locale grammar. Grouped integers are validated structurally against `primaryGroupSize`, `secondaryGroupSize`, and the locale's minimum grouping threshold (e.g. in `es-ES`, `pl-PL`, `lv-LV`, `pt-PT`, 4-digit numbers like `1000` remain ungrouped; grouping begins at 5 digits like `10.000` or `10 000`). Grouping in fractional parts or misplaced separators are strictly rejected.
    - **Edit Mode (`mode: "edit"`):** Optimized for interactive typing with symmetric alternate decimal separator support (`.` in comma-decimal locales like `de-DE` and `tr-TR`, `,` in dot-decimal locales like `en-US`), allowing seamless keypad entry and single-digit edits.
  - **Isolated Paste Transaction Lifecycle:** Clipboard paste transactions are strictly isolated from normal typing sessions. If a pasted payload is non-canonical or rejected, the paste transaction state resets immediately, preventing sticky paste mode and allowing subsequent keystrokes to operate in normal interactive edit mode.
  - **Digit Normalization & Precision:** Automatically normalizes localized Unicode digit scripts (Arabic-Indic, Eastern Arabic-Indic, Devanagari, Bengali, astral numbering systems) and minus signs during parsing while preserving exact numeric precision without UTF-16 code unit inflation.
- **`TimeSelectorComponent`:** Uses locale-aware 2-digit number formatting.
- **`ProgressBarComponent`:** Formats progress percentages according to `localeId()`.
- **`CalendarComponent` & Pickers:** Utilize Luxon locale formatting linked to `localeId()`.

This eliminates synchronization issues between Angular's static `LOCALE_ID` and dynamic runtime locale switches.

### Component Numeric & Date Policies

- **Calendar Gregorian Calendar Policy, Numerals & Locale-Derived Week Start:**
  - Date and time components (`Calendar`, `DatePicker`, `TimePicker`, `DateTimePicker`) format and parse using an explicit Gregorian output calendar (`outputCalendar: "gregory"`). Locales whose platform default is non-Gregorian (such as Persian or Buddhist) format and label the underlying Gregorian date, ensuring semantic dates are preserved across locale switches without misinterpreting Gregorian day numbers.
  - Header month/year and today labels use locale-native token ordering (`toLocaleString({ year: "numeric", month: "long" })`) rather than hard-coded English format strings.
  - Day, year, and decade grid numbers use ASCII / Latin digits (`0-9`) by design to guarantee uniform tabular cell widths, alignment, and dense grid legibility across all locales.
  - **Locale-Derived Week Start & Precedence:** When `firstDay` is omitted or `null`, `CalendarComponent` automatically derives the first day of the week from the active locale (`Intl.Locale.weekInfo.firstDay`, supporting all 7 days: `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday`). For example, `en-US` and `ja-JP` start on Sunday, `de-DE`, `es-ES`, and `fr-FR` start on Monday, and `ar-EG` starts on Saturday. When `firstDay` is explicitly provided by the application, the explicit override takes precedence and remains authoritative across runtime locale switches.
    Mona first uses the runtime `Intl.Locale` week-info API when available. When that API is unavailable, Mona resolves week start through a deterministic fallback pipeline pinned to Unicode CLDR 46:
    1. Explicit Unicode `u-fw-*` first-day overrides take precedence (private-use `-x-` extensions are strictly treated as terminal, preventing opaque payloads from leaking into override resolution).
    2. Territories are resolved via `Intl.Locale` or canonicalized via `Intl.getCanonicalLocales()` (including mapping numeric UN M49 codes to alpha-2 territories), then matched against pinned CLDR 46 territory weekData.
    3. If no territory is present, likely territory week start is resolved from pinned CLDR 46 likely-subtag data (supporting base languages such as `en`, `ja`, `pt`, `he`, `hi`, `ar`, `fa`, language-script tags such as `zh-Hant`, and undefined-language tags such as `und`, `und-Hant`, `und-Arab`, `und-Latn`).
    4. Unresolved or unknown locales default deterministically to Monday (`"001"`).
    The pinned fallback data is generated from pinned CLDR 46 data sources (`weekData.json` and `likelySubtags.json`) via `npm run generate:cldr-week-data` and verified in CI via `npm run check:cldr-week-data`.
  - **Week Numbers & Navigation Boundaries:** Week numbers follow ISO 8601 calculation standards, generalized to any week-start configuration by resolving the ISO week of the Thursday within the row. Keyboard navigation with `Home` and `End` keys in month view navigates to the first and last day of the currently displayed week row according to the effective first day of the week.
- **Date & Time Pickers Locale-Derived Format Policy:**
  - `DatePicker`, `TimePicker`, and `DateTimePicker` automatically derive editable input formats from the active locale when their `format` input is omitted or `null`. For example, `DatePicker` derives `yyyy/MM/dd` for `ja-JP`, `MM/dd/yyyy` for `en-US`, and `dd.MM.yyyy` for `de-DE`.
  - **Explicit Format Precedence:** An application-provided `format` input is authoritative and always takes precedence over auto-derived defaults across runtime locale switches.
  - **`hourFormat` and `showSeconds`:** In auto-derived mode, `hourFormat="12"` positions the day-period token in its native locale position (prefix for `ja-JP` like `ahh:mm`, suffix for `en-US` like `hh:mm a`), while `hourFormat="24"` generates 24-hour patterns (`HH:mm`). `showSeconds=true` includes seconds (`HH:mm:ss` / `ahh:mm:ss` / `hh:mm:ss a`). These options affect only auto-derived formats; explicit formats are preserved verbatim.
  - **Editable Whitespace Normalization:** In generated editable format patterns, non-standard typographic separators (such as non-breaking space `\u00A0` and narrow no-break space `\u202F` emitted by ICU/Intl) are normalized to ordinary ASCII space (` `), allowing users to type standard spaces on standard keyboards while preserving locale punctuation and token ordering. Parsing via `parseGregorianDate` also accepts space variations transparently.
- **Public Locale Format Helpers (`@nanahoshi/mona-ui/i18n`):**
  - Applications and consumers can directly access locale-derived formatting and calendar metadata:
    - `getLocaleDateInputFormat(locale: string): string`
    - `getLocaleTimeInputFormat(locale: string, options?: { hourFormat?: "12" | "24"; showSeconds?: boolean }): string`
    - `getLocaleDateTimeInputFormat(locale: string, options?: { hourFormat?: "12" | "24"; showSeconds?: boolean }): string`
    - `getLocaleFirstDayOfWeek(locale: string): LocaleFirstDayOfWeek`
- **Pager Page Status & Accessible Sentences:**
  - `MonaPagerMessages` provides `pageStatus(page: number, totalPages: number): string` (default: `Page ${page} of ${totalPages}`) and canonical `rangeStatus(start: number, end: number, total: number): string` (default: `${start} - ${end} of ${total} items`) for complete, grammatically natural localized sentences.
  - The numeric page input in both numeric and input modes uses `pageStatus(...)` for its accessible `aria-label` attribute, ensuring screen readers announce the complete context.
  - Individual visual tokens (`pageText`, `ofText`) are available for compact visual layouts.
- **Chart Localized Separators:**
  - Chart tooltips and summary legends utilize `messages().labelValueSeparator` (default: `: `) instead of hardcoded punctuation, allowing locales with different punctuation rules to customize separators.

## 10. Pseudo-Localization & Quality Guardrails

Mona UI includes a reusable pseudo-localization engine (`en-XA`) for verifying internationalization completeness:

```typescript
import { generatePseudoLocale, pseudoLocalize } from '@nanahoshi/mona-ui/i18n';
import { PAGER_DEFAULT_MESSAGES } from '@nanahoshi/mona-ui/pager';

const pseudoLocale = generatePseudoLocale({
    pager: PAGER_DEFAULT_MESSAGES
});

i18n.use(pseudoLocale);
```

### Features
- Accented glyph replacement (e.g. `Apply` -> `[!! Åþþļŷ~~ !!]`).
- Visual text expansion to detect clipped controls, fixed widths, and overflow issues.
- Bracket wrappers (`[!! ... !!]`) to identify truncated strings.
- Automated preservation of interpolation placeholders `{0}`, `{name}`, `{{val}}`, and HTML tags.

## 11. Audit & CI Verification

Mona UI includes a strict AST-based audit scanner (`audit-i18n-rtl.ts`) powered by Angular Compiler and `ts-morph`:
- Scans Angular HTML templates for hard-coded text nodes, static ARIA attributes, and physical style bindings.
- Scans TypeScript files for unlocalized UI literals, static component host metadata, and computed accessibility labels.
- Scans SCSS, CSS, and Tailwind classes for physical styling (`ml-*`, `mr-*`, `left:*`, `right:*`).
- Validates that zero untranslated UI strings or unapproved physical properties exist in the library.

Run the audit locally with:

```bash
npm run audit:i18n-rtl:strict
```

### CLDR Week Data Verification

Mona UI verifies that generated CLDR territory and likely-subtag week start tables match pinned sources:

```bash
npm run check:cldr-week-data
```

To regenerate the pinned fallback tables when adopting a new CLDR baseline:

```bash
npm run generate:cldr-week-data
```
