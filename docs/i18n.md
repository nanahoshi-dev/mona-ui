# Mona UI Internationalization (i18n) & RTL Guide

Mona UI provides a comprehensive, signal-based internationalization (i18n) and localization architecture designed for modern Angular applications.

---

## 1. Core Principles

- **Zero-Config English:** Applications work out of the box with built-in English fallbacks. No setup or provider registration is required if you only need English.
- **Reactive Runtime Locale Switching:** Switching locales via `MonaI18nService.use()` instantly updates all rendered components across the application without requiring page reloads or component re-instantiation.
- **Strictly-Typed Namespaces:** Message interfaces are strongly typed per component namespace (`MonaLocaleMessages`), preventing typos and enabling full autocomplete.
- **Hierarchical Precedence:** A predictable cascade governs all user-facing strings (Component Input > Runtime Override > Active Locale > Component English Fallback).
- **Separation of Locale and Layout Direction:** Translation locale metadata (`MonaLocale.direction`) is strictly decoupled from physical DOM layout direction. Mona components follow the actual inherited DOM/CDK direction (`dir="ltr"` or `dir="rtl"`).

---

## 2. Official Locales (`@nanahoshi/mona-ui/locales`)

Mona UI provides official, framework-maintained locale packages exported via the secondary entry point:

```typescript
@nanahoshi/mona-ui/locales
```

Each locale is also its own entry point, `@nanahoshi/mona-ui/locales/<folder>` (for example `@nanahoshi/mona-ui/locales/de-de`), which exports only that locale's constant. `loadMonaLocale` imports these lazily, so each catalog is a separate chunk that is downloaded only when its locale is loaded (see [Loading Locales Lazily](#loading-locales-lazily)).

| `ko-KR` | Korean (South Korea) | `MONA_KO_KR_LOCALE` | LTR | Complete |

- **Regional Scope Note:** Regional variants are separate locales and are not aliases (e.g., `ar-SA` is Arabic for Saudi Arabia, distinct from other Arabic dialects, and generic tags like `ar` and `ar-Arab` are not aliases; `fr-FR` is French for France, distinct from `fr-CA`; `id-ID` is Indonesian for Indonesia and is distinct from Malay (`ms-MY`), and generic or legacy forms such as `id`, `id_ID`, and `in-ID` are not Mona aliases for `MONA_ID_ID_LOCALE`; `it-IT` is Italian for Italy, distinct from Swiss Italian `it-CH`, and generic tags like `it` and `it_IT` are not aliases; `pt-BR` is Brazilian Portuguese, distinct from European Portuguese `pt-PT` and generic `pt`; `ru-RU` is Russian for Russia and is distinct from regional Russian variants, and generic or noncanonical tags like `ru`, `ru_RU`, and `ru-Cyrl` are not Mona aliases for `MONA_RU_RU_LOCALE` (no automatic mapping is provided for `ru-BY` or `ru-KZ`); `tr-TR` is Turkish for Türkiye, distinct from potential regional variants such as `tr-CY`, and generic tags like `tr` and `tr_TR` are not aliases; `ja-JP` is Japanese for Japan, with no generic `ja` alias; `ko-KR` is Korean for South Korea, with no generic `ko` alias; `zh-CN` is mainland Simplified Chinese and `zh-TW` is Taiwan Traditional Chinese, maintained as two distinct regional localizations with regional terminology rather than a character-conversion layer, and generic tags like `zh`, `zh-Hans`, and `zh-Hant` are not aliases). The constants are never aliased; `loadMonaLocale` is the one place that maps other tags to an official catalog, by language and script (see [Loading Locales Lazily](#loading-locales-lazily)).
- **Zero Configuration for English:** English (`en-US`) is built directly into all component families as default fallbacks. No application requires importing `@nanahoshi/mona-ui/locales` unless opting into an official non-English locale.
- **Official vs. Application-Defined Locales:**
  - **Official Mona Locales:** Complete catalogs maintained by Mona UI. Each is written as JSON (ICU MessageFormat), and its TypeScript is generated from that JSON (see [Catalog Sources](#catalog-sources)). Official locale catalogs are compile-time structurally complete via `satisfies MonaLocaleMessages`: every required namespace, message key, and function signature must be implemented. Linguistic correctness is enforced separately through locale review and locale-specific tests/audits. A future addition of a required key causes compilation to fail until the translation is added.
  - **Application-Defined Locales:** Defined using `MonaLocale` with partial message subsets (`DeepPartial<MonaLocaleMessages>`). Any omitted keys automatically fall back to the component default English catalog.
- **Direction Separation:** Official locale direction metadata (e.g., `MONA_AR_SA_LOCALE.direction`, `MONA_ES_ES_LOCALE.direction`, `MONA_DE_DE_LOCALE.direction`, `MONA_FR_FR_LOCALE.direction`, `MONA_ID_ID_LOCALE.direction`, `MONA_IT_IT_LOCALE.direction`, `MONA_JA_JP_LOCALE.direction`, `MONA_KO_KR_LOCALE.direction`, `MONA_PT_BR_LOCALE.direction`, `MONA_RU_RU_LOCALE.direction`, `MONA_TR_TR_LOCALE.direction`, `MONA_ZH_CN_LOCALE.direction`, `MONA_ZH_TW_LOCALE.direction`) describes the language's conventional reading direction (`ltr` or `rtl`). Selecting an official locale does not mutate DOM `dir`, CDK directionality, or semantic direction roots. Layout and interaction direction continue to follow semantic document/CDK directionality. For example, activating `MONA_AR_SA_LOCALE` provides Arabic translations and exposes `direction: "rtl"`, but `document.documentElement.dir` is never modified by Mona i18n services.

### Using an Official Locale at Startup

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideMonaI18n } from '@nanahoshi/mona-ui/i18n';
import { MONA_DE_DE_LOCALE } from '@nanahoshi/mona-ui/locales';

export const appConfig: ApplicationConfig = {
    providers: [
        provideMonaI18n({
            locale: MONA_DE_DE_LOCALE
        })
    ]
};
```

### Loading Locales Lazily

Importing a constant from `@nanahoshi/mona-ui/locales` bundles that catalog into the chunk that imports it. To download a catalog only when it is needed, configure a loader and load locales by id:

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideMonaI18n } from '@nanahoshi/mona-ui/i18n';
import { loadMonaLocale } from '@nanahoshi/mona-ui/locales';

export const appConfig: ApplicationConfig = {
    providers: [
        provideMonaI18n({
            loadLocale: loadMonaLocale,
            // Loaded before the application starts, so the first render is already localized
            initialLocale: 'de-DE'
        })
    ]
};
```

```typescript
await inject(MonaI18nService).load('de-DE');
```

`loadMonaLocale(localeId)` resolves a locale id as follows:

| Requested id | Result |
|---|---|
| An official id, or its POSIX form (`de-DE`, `de_DE`) | The official constant (`MONA_DE_DE_LOCALE`) |
| The same language and script as an official locale (`de-AT`, `fr-CA`, `ar-EG`, `zh-HK`, `zh-SG`) | That catalog under the requested id: `de-AT` gets German messages, while numbers and dates follow Austrian conventions. Chinese is matched by script, so `zh-HK` gets Traditional Chinese (`zh-TW`) and `zh-SG` gets Simplified Chinese (`zh-CN`). |
| Any other id (`nl-NL`, `he-IL`) | A locale with no messages, so components show their English defaults, while numbers and dates follow the requested id. Its `direction` comes from its script, so `he-IL` and `fa-IR` are `rtl`. |

`MONA_OFFICIAL_LOCALE_IDS` lists the ids that have a catalog.

`MonaI18nService.load(localeId)`:

- Canonicalizes the id and loads each locale once. Later calls reuse it, and concurrent calls for the same id share one request.
- Lets the latest `load()` or `use()` win. When a newer one starts before an earlier one finishes, the earlier one resolves without switching.
- Exposes `loading` (a load is in progress) and `loadError` (the error of the latest failed load) as signals.
- On failure, keeps the current locale, sets `loadError` and rejects. The failed locale is not cached, so calling `load()` again retries it.

When `initialLocale` fails to load, the application still starts, with `locale` (or English), and the error is logged.

`loadLocale` can be any function that resolves to a `MonaLocale`, for example one that fetches a catalog from your server, or one that falls back to `loadMonaLocale`:

```typescript
provideMonaI18n({
    loadLocale: id => (id === 'nl-NL' ? import('./locales/nl-nl').then(m => m.NL_NL_LOCALE) : loadMonaLocale(id))
});
```

### Catalogs as Data (ICU MessageFormat)

Translation-management systems such as Crowdin, Lokalise and Phrase export JSON, not TypeScript functions. `@nanahoshi/mona-ui/i18n/icu` compiles a catalog written as data into a `MonaLocale`. Every message is a string, and messages with parameters use ICU MessageFormat:

```json
{
    "id": "de-DE",
    "direction": "ltr",
    "messages": {
        "pager": {
            "nextPageLabel": "Nächste Seite",
            "pageStatus": "Seite {page, number} von {totalPages, number}",
            "jumpForwardLabel": "{pages, plural, one {Um # Seite vorspringen} other {Um # Seiten vorspringen}}"
        },
        "chip": {
            "removeLabel": "{label, select, undefined {Element entfernen} other {{label} entfernen}}"
        }
    }
}
```

```typescript
import { compileMonaLocale } from '@nanahoshi/mona-ui/i18n/icu';

provideMonaI18n({
    loadLocale: id =>
        fetch(`/i18n/${id}.json`)
            .then(response => response.json())
            .then(data => compileMonaLocale(data))
});
```

- **Keys and parameters.** Namespaces and keys are those of `MonaLocaleMessages`. Parameter names are the names in the message's TypeScript signature: `pageStatus(page: number, totalPages: number)` takes `{page}` and `{totalPages}`. `MONA_MESSAGE_PARAMETERS` lists them for every message, and is generated from the message types (`npm run generate:message-parameters`; `test:audit` fails when it is out of date).
- **Supported syntax** (a subset of ICU, with no runtime dependency):
  - `{name}`, and `{name, number}` with the `integer` and `percent` styles or the `::group-off`, `::percent` and `::precision-integer` skeletons. Years are usually `{year, number, ::group-off}`.
  - `{name, plural, ...}` and `{name, selectordinal, ...}` with `=N` and CLDR category selectors, `offset:N`, and `#`.
  - `{name, select, ...}`.
  - Apostrophe quoting: `''` is an apostrophe, and `'{'`, `'}'` and, inside a plural, `'#'` are literal.
  - Date and time arguments are rejected, because no Mona message takes one. Every `plural` and `select` needs an `other` option.
- **Numbers** are formatted with the locale's digits and grouping, the same as the official catalogs, so `{page}` is `1.200` in German (`de-DE`) and `١٢` in Egyptian Arabic (`ar-EG`).
- **Optional parameters.** A `select` on an absent or empty parameter picks the `undefined` option, then `other`.
- **Bad input never breaks the page.** A message with an unknown key or parameter, a type mismatch (a `plural` on a string parameter) or a syntax error is skipped, so components show the English default for it, and a dev-mode warning lists every issue. `compileMonaLocale(data, { strict: true })` throws a `MonaLocaleDataError` with the issues instead.
- **Checking catalogs in CI.** `validateMonaLocaleData(data)` returns the same issues without compiling, each with a `code` and a `path` such as `messages.pager.pageStatus`. An empty array means the catalog compiles cleanly.

`@nanahoshi/mona-ui/i18n/icu` is its own entry point (about 5 KB gzipped, most of it the parameter table), so applications that don't import it don't download it.

**The official catalogs as JSON.** Every official catalog is also in the package as the JSON it is generated from, so you can seed a translation-management system with it, or patch a copy and compile it at runtime:

| Catalog | Specifier |
|---|---|
| English | `@nanahoshi/mona-ui/i18n/catalogs/en-US.messages.json` |
| An official locale | `@nanahoshi/mona-ui/locales/<folder>/<folder>.messages.json`, for example `@nanahoshi/mona-ui/locales/de-de/de-de.messages.json` |

Each file holds the `messages` of a `MonaLocaleData`, so it compiles with its id and direction:

```typescript
import messages from '@nanahoshi/mona-ui/locales/de-de/de-de.messages.json';

const locale = compileMonaLocale({ direction: 'ltr', id: 'de-DE', messages });
```

## 3. Configuration & Providers

To configure Mona UI with an initial locale or custom message overrides, use `provideMonaI18n()` in your application config:

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideMonaI18n } from '@nanahoshi/mona-ui/i18n';
import { MONA_TR_TR_LOCALE } from '@nanahoshi/mona-ui/locales';

export const appConfig: ApplicationConfig = {
    providers: [
        provideMonaI18n({
            locale: MONA_TR_TR_LOCALE,
            messages: {
                pager: {
                    firstPageLabel: 'Başlangıç'
                }
            },
            // Applied only while that locale is active
            localeMessages: {
                'de-DE': {
                    pager: {
                        firstPageLabel: 'Anfang'
                    }
                }
            }
        })
    ]
};
```

- **`messages`** applies whatever the active locale is.
- **`localeMessages`** is keyed by locale id and applies only while that locale is active. Keys are canonicalized, so `de_DE` and `de-DE` are the same key.
- **`loadLocale`** loads a locale by id for `MonaI18nService.load()`, usually `loadMonaLocale`. See [Loading Locales Lazily](#loading-locales-lazily).
- **`initialLocale`** is a locale id loaded with `loadLocale` before the application starts.

## 4. The `MonaLocale` Contract

A Mona locale is defined by:

```typescript
export interface MonaLocale {
    /** BCP 47 locale tag, e.g. "en-US", "de-DE", "tr-TR", "ar-SA" */
    readonly id: string;

    /** Conventional writing direction associated with the locale ("ltr" or "rtl") */
    readonly direction: 'ltr' | 'rtl';

    /** Deep partial messages structured by component namespace */
    readonly messages: DeepPartial<MonaLocaleMessages>;
}
```

### Typed Message Namespaces

Each component family owns a distinct message namespace under `MonaLocaleMessages`, such as:
- `autoComplete`
- `breadcrumb`
- `calendar`
- `chart`
- `editor`
- `filter`
- `grid`
- `numericTextBox`
- `pager`
- `scrollView`
- `tabs`
- ...and all other Mona UI components.

Typo namespaces fail at compile-time:

```typescript
const invalidLocale: MonaLocale = {
    id: 'en-US',
    direction: 'ltr',
    messages: {
        // @ts-expect-error Typos fail compile-time validation
        pagre: {}
    }
};
```

## 6. Runtime Message Overrides

If you want to customize specific strings across the entire application without replacing the active locale, use the override APIs:

- **`setMessages(overrides, options?)`**: Replaces the existing overrides.
- **`patchMessages(partialOverrides, options?)`**: Merges new overrides into existing ones without discarding others.
- **`clearMessages(options?)`**: Removes overrides, restoring the active locale's values. Without `options.locale`, every override is removed, global and per locale.

Without `options`, overrides are global and stay in effect after `use()` switches the locale. Pass `{ locale }` to scope them to one locale, so a German label you patch does not show after switching to English:

```typescript
// Override pager labels globally
i18n.patchMessages({
    pager: {
        nextPageLabel: 'Next >>'
    }
});

// Only while de-DE is active
i18n.patchMessages({ pager: { nextPageLabel: 'Weiter' } }, { locale: 'de-DE' });

// Remove the de-DE overrides only
i18n.clearMessages({ locale: 'de-DE' });

// Remove every override
i18n.clearMessages();
```

## 7. Message Override Precedence

When a component resolves a user-facing label or announcement, the resolution order is strictly:

1. **Explicit Component Input:** A direct property binding on the component (e.g. `[aria-label]="'Custom'"` or custom templates).
2. **Per-Locale Overrides:** `localeMessages`, or `setMessages()` / `patchMessages()` called with `{ locale }`, for the active locale.
3. **Global Overrides:** `messages`, or `setMessages()` / `patchMessages()` called without a locale.
4. **Active Locale Messages:** Messages provided in the current `MonaLocale` via `use()`.
5. **Component English Fallback:** Built-in default English catalog.

## 8. Locale vs. Layout Direction (RTL Architecture)

> [!IMPORTANT]
> `MonaLocale.direction` describes the conventional writing direction of the translation language. Mona UI does **NOT** automatically mutate `<html dir="...">` or subtree `dir` attributes.
>
> All direction-sensitive component behaviors (keyboard arrow navigation, animations, carousels, progress bar clipping, scroll offsets) follow the **semantic document directionality** resolved hierarchically:
> 1. **Connected Browser Semantic Direction (`:dir(rtl)` / `:dir(ltr)`):** In connected browser environments supporting `:dir()`, the browser's semantic document directionality is resolved (including native first-strong character resolution for `dir="auto"`). This guarantees exact alignment with Tailwind's `rtl:` and `ltr:` conditional variant styles.
> 2. **Explicit Ancestor `[dir]` Hierarchy:** In unattached DOM trees or environments without `:dir()` support, the nearest valid ancestor `dir` attribute (`ltr`, `rtl`, or `auto`) is resolved.
> 3. **Angular CDK `Directionality`:** Application-level direction fallback.
> 4. Default fallback: `'ltr'`.
>
> Mona's direction-sensitive behavior follows semantic document directionality (`dir`, inherited HTML directionality, and CDK direction state). Do not use the CSS `direction` property alone to switch Mona components between LTR and RTL behavior.

This ensures full support for:
- An Arabic locale rendered inside an LTR technical layout (`dir="ltr"`).
- An English locale rendered inside an RTL layout (`dir="rtl"`).
- Mixed LTR and RTL subtrees co-existing on the same page under a single `MonaI18nService` instance.

### RTL Guarantees & Logical Interactions

Mona UI provides complete **RTL and logical-layout support**:

#### Preferred Default: CSS Logical Properties & Utilities
For ordinary content, padding, margins, and layout flow that naturally follow the CSS writing direction:
- **CSS Logical Properties:** General UI layouts use CSS Logical Properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start/end`).
- **Logical Tailwind Utilities:** Tailwind utility classes use logical equivalents (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`).

#### Intentional Semantic-Physical Layout Exceptions
For interaction-critical geometry whose behavioral axis follows Mona semantic direction (`dir` attribute / CDK directionality) and must remain stable even when CSS `direction` is independently overridden, Mona explicitly maps semantic `start/end` to physical `left/right` coordinates:
- **Slider & RangeSlider:** Handles, selection fill bands, ticks, and label coordinates map semantic start/end to physical left/right coordinates to ensure the visual track and keyboard navigation direction match semantic direction even when CSS writing direction is decoupled.
- **Sidebar Docked Layout & Drawers:** Start and end sidebars, interior separator borders, collapse rail edges, and offcanvas drawer translations map to explicit physical coordinates according to semantic direction.
  > [!NOTE]
  > Computed CSS direction may be read as a rendering-compensation input; it does not become Mona's semantic behavior source.
- **ScrollView:** Carousel Previous/Next navigation controls pin to explicit physical edges according to semantic direction, and directional chevron icons mirror orientation (`rtl:rotate-180`).

These exceptions are **deliberate**, **strictly audited** via the i18n scanner, **narrowly allowlisted**, and **end-to-end browser tested** across all four LTR/RTL and split-direction matrices.

#### Direction-Aware Behaviors & Tracking
- **Icon Mirroring:** Directional chevrons and navigation arrows automatically mirror in RTL (`rtl:rotate-180`).
- **Direction-Aware Keyboard Navigation:**
  - **Pager:** Arrow keys navigate logically (`ArrowLeft` navigates to the next page in RTL, previous page in LTR; `ArrowRight` navigates to the previous page in RTL, next page in LTR).
  - **Calendar:** Arrow keys step forward/backward logically across day, month, year, and decade cells (`ArrowLeft` steps forward by 1 unit in RTL, backward in LTR; `ArrowRight` steps backward in RTL, forward in LTR).
  - **Slider & RangeSlider:** Arrow keys increase/decrease values in accordance with semantic direction (in RTL, `ArrowLeft` increases value and moves the handle leftward; `ArrowRight` decreases value and moves the handle rightward).
- **Logical Drag & Resize:**
  - **Grid Column Resizing:** Resize delta is inverted in RTL layouts so dragging in the visual inline-end direction increases column width and dragging inline-start decreases it intuitively.
- **Direction-Aware Visual Encodings:**
  - **Chart Color Scales:** Horizontal color scales and gradients mirror orientation in RTL to maintain logical scale progression.
  - **Chart Frame:** The title, legend order, tooltip text, automatic data labels and the default Y axis follow the direction, and `start` and `end` positions follow it too, while `left` and `right` stay on that side. The X axis keeps its left-to-right order, so categories and time read the same in both directions.
- **Subtree Direction Tracking & Reactive Boundaries:**
  - Direction-sensitive components observe changes via MutationObserver for semantic `dir` attribute changes (`ltr`, `rtl`, `auto`), content mutations inside `dir="auto"` subtrees (re-evaluating first-strong directional characters), and Angular CDK `Directionality` changes.
  - **Reactive Boundary:** Runtime updates must be performed via semantic `dir` attributes or Angular CDK directionality. CSS `direction` alone does not match Tailwind's `:dir()` variants and is outside the component behavioral direction boundary. Moving components across pre-existing direction roots (reparenting) should be accompanied by updating semantic `dir` attributes.

---

### Popup Language (`lang`)

Mona never sets `lang` on your document; that is the application's job (WCAG 3.1.1). Popups are the exception: the CDK overlay container is rendered at the end of `<body>`, outside any `lang` you put on your app root, so screen readers could read localized popup text with the wrong voice (WCAG 3.1.2). Each popup pane therefore gets a `lang` attribute:

1. the nearest `lang` above the popup's anchor (dialogs and windows anchor to `<body>`, so they take `<html lang>`);
2. otherwise, the active `MonaI18nService.localeId()`.

## 9. Formatting & Angular `LOCALE_ID` Independence

Mona UI components format numbers, currencies, dates, and times using `MonaI18nService.localeId()` directly:
- **`NumericTextBoxComponent` & Locale Formatters:**
  - **Dynamic Grouping Pattern Derivation:** Automatically discovers the locale's primary and secondary grouping sizes, canonical group separator, and minimum grouping threshold from `Intl.NumberFormat`:
    - **Western Grouping:** 3-3-3 digit groupings (e.g. `1,234,567.89` in `en-US`, `1.234.567,89` in `de-DE`).
    - **Indian Grouping:** 3-2-2 digit groupings (e.g. `1,23,45,678.9` in `hi-IN`, `en-IN`, `bn-BD`, `mr-IN`).
    - **Arabic & Eastern Numbering:** Canonical Arabic thousand separator (`\u066C`) and Arabic-Indic / Eastern Arabic-Indic digits (e.g. `ar-SA`, `fa-IR`).
    - **Space-Delimited Separators:** Strictly accepts canonical space variants (regular space `\u0020`, non-breaking space `\u00A0`, narrow no-break space `\u202F`) while rejecting other whitespace (tabs, newlines, form feeds) in strict mode (e.g. `fr-FR`).
  - **Strict ("locale") vs. Interactive ("edit") Parsing Modes:**
    - **Strict Mode (`mode: "locale"`):** Enforces canonical locale grammar. Grouped integers are validated structurally against `primaryGroupSize` and `secondaryGroupSize`. Grouping below the locale's formatting threshold is accepted: `es-ES`, `pl-PL`, `lv-LV` and `pt-PT` format 4-digit numbers ungrouped (`1000`), but a pasted `1.000` or `1 000` is still read as 1000. In locales that group with an apostrophe (`de-CH`), `'`, `’` and `ʼ` are all accepted, because engines disagree on the character (Node ICU `'`, Chrome `’`) and keyboards type `'`. Grouping in fractional parts or misplaced separators are strictly rejected.
    - **Edit Mode (`mode: "edit"`):** Optimized for interactive typing. Besides the locale decimal, `.` and `,` are accepted as alternate decimal separators **unless the alternate is the locale's group separator**. So `.` works in `fr-FR` (space grouping) and `,` in `de-CH` (apostrophe grouping), but typing `,` in `en-US` or `.` in `de-DE` / `tr-TR` is rejected instead of being read as a decimal. Typing `1,234` in `en-US` therefore yields `1234`, the same value as pasting it, never `1.234`. The numpad decimal key always inserts the locale's decimal separator, whatever the keyboard layout types.
  - **No Silent Rounding:** A JavaScript `number` cannot hold every decimal value exactly, so parsing refuses input it would change instead of rounding it. Accepted are integers up to `Number.MAX_SAFE_INTEGER` (`9007199254740991`), and values with a fraction of at most 15 significant digits; leading and trailing zeros do not count. `parseLocalizedNumber("9007199254740993", "en-US")` returns `null` rather than `9007199254740992`. `validateLocalizedNumber` and `validateLocalizedNumberEdit` say why a value was refused with `reason`: `"syntax"` (not a number in the locale), `"decimals"` (too many fraction digits) or `"precision"`. `NumericTextBoxComponent` blocks the keystroke or paste that would lose precision, and its spin buttons stop at `±Number.MAX_SAFE_INTEGER`. A value set programmatically is still displayed as is. For values that need more digits, `parseLocalizedDecimal`, `validateLocalizedDecimal` and `validateLocalizedDecimalEdit` apply the same locale rules but return a canonical decimal string (`"-1234.5"`) with no precision limit, `formatNumber` formats such a string exactly, and `DecimalTextBoxComponent` (`mona-decimal-text-box`) is the text box built on them.
  - **Isolated Paste Transaction Lifecycle:** Clipboard paste transactions are strictly isolated from normal typing sessions. If a pasted payload is non-canonical or rejected, the paste transaction state resets immediately, preventing sticky paste mode and allowing subsequent keystrokes to operate in normal interactive edit mode.
  - **Digit Normalization & Precision:** Automatically normalizes every Unicode decimal digit script (Arabic-Indic, Eastern Arabic-Indic, Devanagari, Bengali, Thai, astral numbering systems), full-width digits and separators typed by CJK input methods (`１２．５`) and minus signs during parsing while preserving exact numeric precision without UTF-16 code unit inflation.
- **`TimeSelectorComponent`:** Uses locale-aware 2-digit number formatting.
- **`ProgressBarComponent`:** Formats progress percentages according to `localeId()`.
- **`CalendarComponent` & Pickers:** Utilize Luxon locale formatting linked to `localeId()`.

This eliminates synchronization issues between Angular's static `LOCALE_ID` and dynamic runtime locale switches.

**Exception: grid date columns with a `format`.** A grid cell whose column has a date `format` renders through Angular's `formatDate`, which takes Angular's `LOCALE_ID` and needs that locale's data registered (`registerLocaleData`). Such cells don't follow `MonaI18nService` locale switches. Keep `LOCALE_ID` aligned with the Mona locale in apps that switch locales, or format those dates in a cell template.

### Component Numeric & Date Policies

- **Calendar Gregorian Calendar Policy, Numerals & Locale-Derived Week Start:**
  - Date and time components (`Calendar`, `DatePicker`, `TimePicker`, `DateTimePicker`) format and parse using an explicit Gregorian output calendar (`outputCalendar: "gregory"`). Locales whose platform default is non-Gregorian (such as Persian or Buddhist) format and label the underlying Gregorian date, ensuring semantic dates are preserved across locale switches without misinterpreting Gregorian day numbers.
  - Header month/year and today labels use locale-native token ordering (`toLocaleString({ year: "numeric", month: "long" })`) rather than hard-coded English format strings.
  - Framework-generated user-visible numeric text (such as Calendar day, week, and decade numbers, Pager page numbers, and Stepper default indicator numbers) is formatted according to the active `MonaI18nService.localeId()`. For example, Arabic (`ar-SA`) renders locale-native Arabic-Indic numerals (`٠-٩`) while dates remain Gregorian. Internal numeric models, event payloads, numeric ARIA state attributes (`aria-valuenow`, `aria-valuemin`, `aria-valuemax`), and custom template contexts remain numeric and are not converted to localized strings. Weekday column headers automatically fall back to compact narrow representations (e.g., Arabic `ح`، `ن`، `ث`، `ر`، `خ`، `ج`، `س`) when short names are lengthy or duplicate the full day name, exposing the compact label accessibly via an `aria-hidden="true"` visible span paired with a `span.sr-only` element providing the full day name for assistive technology.
  - **Locale-Derived Week Start & Precedence:** When `firstDay` is omitted or `null`, `CalendarComponent` automatically derives the first day of the week from the active locale (`Intl.Locale.weekInfo.firstDay`, supporting all 7 days: `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday`). For example, `en-US`, `ar-SA`, `ja-JP`, `ko-KR`, and `zh-TW` start on Sunday, `de-DE`, `es-ES`, `fr-FR`, and `zh-CN` start on Monday, and `ar-EG` starts on Saturday. When `firstDay` is explicitly provided by the application, the explicit override takes precedence and remains authoritative across runtime locale switches.
    Mona first uses the runtime `Intl.Locale` week-info API when available. When that API is unavailable, Mona resolves week start through a deterministic fallback pipeline pinned to unmodified Unicode CLDR 46 sources (`weekData.json` and `likelySubtags.json`).
    Native runtimes may use newer CLDR data (from their host ICU) and can therefore differ from the fallback for territories whose rules changed after CLDR 46. For example, Iceland (`IS`) changed from Monday-first in CLDR 46 to Sunday-first in CLDR 48: a modern native runtime may report Sunday, while Mona's deterministic CLDR 46 fallback reports Monday.
    1. Explicit Unicode `u-fw-*` first-day overrides take precedence (private-use `-x-` extensions are strictly treated as terminal, preventing opaque payloads from leaking into override resolution).
    2. Territories are resolved via `Intl.Locale` or canonicalized via `Intl.getCanonicalLocales()` (including mapping numeric UN M49 codes to alpha-2 territories), then matched against pinned CLDR 46 territory weekData.
    3. If no territory is present, likely territory week start is resolved from pinned CLDR 46 likely-subtag data (supporting base languages such as `en`, `ja`, `pt`, `he`, `hi`, `ar`, `fa`, language-script tags such as `zh-Hant`, and undefined-language tags such as `und`, `und-Hant`, `und-Arab`, `und-Latn`).
    4. Unresolved or unknown locales default deterministically to Monday (`"001"`).
    The pinned fallback data is generated from pinned CLDR 46 data sources (`weekData.json` and `likelySubtags.json`) via `npm run generate:cldr-week-data`, authenticated against cryptographic SHA-256 provenance hashes, and verified in CI via `npm run check:cldr-week-data`.
  - **Week Numbers & Navigation Boundaries:** Week numbers follow ISO 8601 calculation standards, generalized to any week-start configuration by resolving the ISO week of the Thursday within the row. Keyboard navigation with `Home` and `End` keys in month view navigates to the first and last day of the currently displayed week row according to the effective first day of the week.
- **Date & Time Pickers Locale-Derived Format Policy:**
  - `DatePicker`, `TimePicker`, and `DateTimePicker` automatically derive editable input formats from the active locale when their `format` input is omitted or `null`. For example, `DatePicker` derives `yyyy/MM/dd` for `ja-JP`, `zh-CN`, and `zh-TW`, `yyyy. MM. dd.` for `ko-KR`, `MM/dd/yyyy` for `en-US`, `dd.MM.yyyy` for `de-DE`, and `dd/MM/yyyy` for `ar-SA`.
  - **Explicit Format Precedence:** An application-provided `format` input is authoritative and always takes precedence over auto-derived defaults across runtime locale switches.
  - **`hourFormat` and `showSeconds`:** In auto-derived mode, `hourFormat="12"` positions the day-period token in its native locale position (prefix for `ja-JP`, `ko-KR`, `zh-CN`, and `zh-TW` like `a hh:mm` or `ahh:mm`, suffix for `en-US` and `ar-SA` like `hh:mm a`), while `hourFormat="24"` generates 24-hour patterns (`HH:mm`). `showSeconds=true` includes seconds (`HH:mm:ss` / `a hh:mm:ss` / `ahh:mm:ss` / `hh:mm:ss a`). These options affect only auto-derived formats; explicit formats are preserved verbatim.
  - **Editable Whitespace & Bidi Sanitization:** In generated editable format patterns, non-standard typographic separators (such as non-breaking space `\u00A0` and narrow no-break space `\u202F` emitted by ICU/Intl) are normalized to ordinary ASCII space (` `), and invisible bidi-control characters (`[\u061C\u200E\u200F\u202A-\u202E\u2066-\u2069]`) are sanitized so users can cleanly type dates on standard keyboards without hidden formatting traps. Visible locale punctuation (such as the Arabic comma `،`) is preserved, and `parseGregorianDate` accepts both Arabic-Indic (`٠-٩`) and Latin (`0-9`) numerals transparently.
- **Public Locale Format Helpers (`@nanahoshi/mona-ui/i18n`):**
  - Applications and consumers can directly access locale-derived formatting and calendar metadata:
    - `getLocaleDateInputFormat(locale: string): string`
    - `getLocaleTimeInputFormat(locale: string, options?: { hourFormat?: "12" | "24"; showSeconds?: boolean }): string`
    - `getLocaleDateTimeInputFormat(locale: string, options?: { hourFormat?: "12" | "24"; showSeconds?: boolean }): string`
    - `getLocaleFirstDayOfWeek(locale: string): LocaleFirstDayOfWeek`
- **Pager Page Status & Accessible Sentences:**
  - `MonaPagerMessages` provides `pageStatus(page: number, totalPages: number): string` (default: `Page ${page} of ${totalPages}`) and canonical `rangeStatus(start: number, end: number, total: number): string` (default: `${start} - ${end} of ${total} items`) for complete, grammatically natural localized sentences.
  - The numeric page input in both numeric and input modes uses `pageStatus(...)` for its accessible `aria-label` attribute, ensuring screen readers announce the complete context.
  - Individual visual tokens (`pageText`, `ofText`) are available for compact visual layouts.
- **Numbers Inside Messages:**
  - Official locale catalogs and the English defaults format the numbers they interpolate with `formatNumber(value, localeId)` from `@nanahoshi/mona-ui/i18n`, so counts follow the locale's digits, grouping and decimal separator: `Страница 2 из 12 345` in `ru-RU`, `١٢٬٣٤٥` in `ar-SA`, `Page 2 of 12,345` in English. Years (`calendar.yearCellLabel`, `decadeRange`, `decadeViewLabel`) are never grouped.
  - Message functions still receive numbers, so plural rules keep working. Custom catalogs should format the same way:
    ```typescript
    pageStatus: (page: number, totalPages: number) =>
        `Seite ${formatNumber(page, 'de-DE')} von ${formatNumber(totalPages, 'de-DE')}`
    ```
- **Chart Numbers, Dates and Messages:**
  - Axis ticks, data labels, tooltips, the heatmap color scale and screen reader announcements format numbers, percentages and dates for the library locale (`MonaI18nService.localeId()`), not the browser's. Ticks are compact from a thousand up (`1.2M`, `200T` in English, `1,5 Mio.` in German); smaller values are grouped and rounded to at most six decimals. A runtime `load()` or `use()` reformats every chart in place.
  - A series `valueFormatter` or axis `formatter` still takes precedence over the built-in formats.
  - Built-in text comes from the `chart` messages: the waterfall legend (`increase`, `decrease`, `noChange`, `subtotal`, `total`), names for unnamed series, categories, items, stages and steps (`seriesFallbackName` and the like), the tooltip's `valueRange` and `pathSeparator`, and every announcement (`stagePosition`, `ohlcValues`, `itemSelected`, `pannedLeft`, `zoomedIn` and the rest). `announcementSeparator` joins the parts of an announcement (`, ` in English, `、` in Japanese, `，` in Chinese).
  - Chart tooltips and summary legends place `messages().labelValueSeparator` after each label (`:` in English, ` :` with a no-break space in French).

## 10. Pseudo-Localization & Quality Guardrails

Mona UI includes a reusable pseudo-localization engine (`en-XA`) for verifying internationalization completeness:

```typescript
import { generatePseudoLocale, pseudoLocalize } from '@nanahoshi/mona-ui/i18n';
import { PAGER_DEFAULT_MESSAGES } from '@nanahoshi/mona-ui/pager';

const pseudoLocale = generatePseudoLocale({
    pager: PAGER_DEFAULT_MESSAGES
});

i18n.use(pseudoLocale);
```

### Features
- Accented glyph replacement (e.g. `Apply` -> `[!! Åþþļŷ~~ !!]`).
- Visual text expansion to detect clipped controls, fixed widths, and overflow issues.
- Bracket wrappers (`[!! ... !!]`) to identify truncated strings.
- Automated preservation of interpolation placeholders `{0}`, `{name}`, `{{val}}`, and HTML tags.

## 11. Audit & CI Verification

Mona UI includes a strict AST-based audit scanner (`audit-i18n-rtl.ts`) powered by Angular Compiler and `ts-morph`:
- Scans Angular HTML templates for hard-coded text nodes, static ARIA attributes, and physical style bindings.
- Scans TypeScript files for unlocalized UI literals, static component host metadata, and computed accessibility labels.
- Scans SCSS, CSS, and Tailwind classes for physical styling (`ml-*`, `mr-*`, `left:*`, `right:*`).
- Validates that zero untranslated UI strings or unapproved physical properties exist in the library.

Run the audit locally with:

```bash
npm run audit:i18n-rtl:strict
```

### Catalog Sources

The JSON files are the source of every catalog: `projects/mona-ui/i18n/catalogs/en-US.messages.json` for English, and `projects/mona-ui/locales/<folder>/<folder>.messages.json` for each official locale. The TypeScript catalogs, the `*.default-messages.ts` of each component and `<folder>.messages.ts` of each locale, are generated from them and must not be edited by hand.

To change a message, edit the JSON and regenerate:

```bash
npm run generate:locale-catalogs
```

- The generator validates every JSON file with `validateMonaLocaleData`, and fails on any issue or missing message.
- The generated code calls `formatNumber` and `Intl.PluralRules` directly, so no ICU parser runs at runtime and each component keeps its own defaults, as before.
- CI runs `npm run check:locale-catalogs`, which fails when a generated file does not match its JSON.
- `catalog-equivalence.spec.ts` checks that every generated message returns exactly what `compileMonaLocale` makes of its JSON, for numbers that exercise each locale's plural rules and for empty, absent and unusual strings.
- After changing a message type, run `npm run generate:message-parameters` first, so the parameter table the generator reads is current.

### CLDR Week Data Verification & Provenance

Mona UI verifies that generated CLDR territory and likely-subtag week start tables match pinned sources and that vendored source fixtures match their cryptographic SHA-256 hashes in `scripts/cldr/provenance.json`:

```bash
npm run check:cldr-week-data
```

To update or regenerate the pinned fallback tables when adopting a new CLDR baseline:

```bash
npm run update:cldr-week-sources
npm run generate:cldr-week-data
```
